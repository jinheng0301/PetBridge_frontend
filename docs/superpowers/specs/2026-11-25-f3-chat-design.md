# F3 聊天：成员私聊与小屋通知设计

> 日期：2026-11-25 · 对应前端 TRD 第 20 章 W7–8 的 F3 · 后端依赖 B5、B6a（已完成）与本文第 5 节的小改动 · 状态：待确认

## 1. 目的

F2 让同屋的人互相看得到，但“聊天”Tab 还是占位页，不同母语的人没法交流。F3 要让他们**各写各的母语、各看各的母语**（里程碑 M3“跨语言消息可用”）：一对一的话走成员私聊，要对全屋说的话贴在小屋通知里，都由发送者的宠物以信使卡片送到。

用户最看重：**不让用户搞混“这句话谁看得到”**。因此每个成员一个单独会话，全屋消息放在单独的公告板，二者不混在同一个列表。

## 2. 范围

**做（分两段，同一份计划）**

- **后端准备**（第 5 节）：`MessageView.delivery` 可空的契约写法、按会话筛选消息、小屋通知每日条数上限。
- **F3a 会话与收发**
  - 聊天 Tab 首页：会话列表（小屋通知置顶 + 每个成员一行），顶部沿用小屋切换。
  - 私聊页、小屋通知页：历史、翻页、实时新消息、发送文本。
  - 信使卡片：译文 / 润色 / 原文切换，翻译中、失败、已撤回各状态。
  - 本地缓存（drift）、重连补消息、发送失败与手动重试。
- **F3b 增强**
  - 常用短语、发送方润色开关、接收方“让 AI 润色”。
  - 离线自动补发、未读。

**不做**

- **真正的群聊：第二版**（用户决定）。
- 举报、屏蔽的界面：F4。F3 只处理“消息被撤回”（`message.removed`）。
- 表情贴纸（F4.9，P1）、译文点踩（F4.8，P1）：不在 MVP 的 F3。系统键盘的 emoji 按普通文本发送。
- 已读回执、“对方正在输入”、推送：B7 / F5。
- 打卡与装扮的新事件：F4；F3 照旧忽略未知事件。

**反目标**（技术上能跑但算失败）

- 私聊内容出现在小屋通知里，或反过来。
- 断线重连后漏消息、重复气泡，或译文一直停在“翻译中”（服务端其实已译好）。
- 小屋通知用起来像群聊（左右气泡、刷屏）。
- 发送失败的消息悄悄消失，或重启后重复发出。

## 3. 约束

- 协议以后端 TRD 7.4、7.9、第 9 章为准：发送走 REST，结果走 WS（`message.new` / `message.translated` / `message.polished` / `message.removed`，都不带 seq，只投给订阅了该房间的连接）。
- 文本 1–500 字；每人每分钟 20 条、每日 1000 条；私聊双方都必须成年，且都在席。
- 未成年人（`age_band = 13_17`）不能私聊，只能用小屋通知。
- 后端 worker 必须在运行（`task worker`），否则译文不会回来。
- 五种界面语言；简繁文案分别写，不混字。
- **排期**：B6b 正在另一个会话里改后端 `openapi.yaml` 与两个仓库的三份文档。**第 5 节的契约改动、重新生成客户端、三份文档同步，都等 B6b 提交之后再做**，并以它提交后的版本号为基础递增。
- F2 双机验收在动 F3 代码前做完（聊天复用同一条实时连接）。

## 4. 做法比较（用户已选）

**私聊放在哪里**

| | 做法 | 取舍 |
| :-- | :-- | :-- |
| A | 同一列表，发送时选收件人 | 后端不用改；可能发错对象，群聊与悄悄话混在一起 |
| **B（已选）** | 每个成员一个单独会话，全屋消息另放公告板 | 谁看得到一目了然；多一层会话列表与分会话未读 |
| C | F3 只做群聊 | 最快；F4.1 的私聊缺口留到以后 |

**会话历史从哪里来**

| | 做法 | 取舍 |
| :-- | :-- | :-- |
| **1（已选）** | 后端消息接口加可选筛选条件，按会话翻页 | 后端改动小；换手机、重装后一样快；翻页逻辑简单 |
| 2 | 手机下载全部消息自己分组 | 后端不改；首次要下载最多 30 天，下载完之前列表不完整 |
| 3 | 后端新建 conversations 表与会话接口 | 最完整（服务端未读、会话摘要），但一间小屋最多 5 人用不上，放弃 |

## 5. 后端改动

1. **契约**：`MessageView.delivery` 在发送者视角是 `null`，但现在 `required` + `allOf` + `nullable` 的写法让 swagger_parser 生成了不可空字段，发送响应与自己的历史消息都会解析失败。服务端行为不变（始终输出该键，值可为 null），只改 `openapi.yaml` 的写法，使生成的字段为 `DeliveryView?`。先试把 `delivery` 移出 `required`；仍不行再升级 swagger_parser。后端契约测试必须照样通过；前端 `contract_decode_test` 加一条“delivery 为 null”与一条“delivery 有值”。
2. **按会话筛选**：`GET /rooms/{id}/messages` 新增两个可选查询参数，与 `before` / `after` / `limit` 可组合：
   - `scope=room`：只返回全屋消息（小屋通知）。
   - `peer_id=<uuid>`：只返回调用者与该用户之间的私聊（双向）。对方已离席也照常返回历史；查不到就是空列表。
   - 两者都不给：与现在相同（混合）。两者同时给、`scope` 不是 `room`、`peer_id` 不是 UUID 或等于自己：400 `VALIDATION_FAILED`，`fields` 列出对应参数。
   - 可见性规则（delivery、屏蔽、审核隐藏、在席）全部不变，筛选只是再收窄。
   - 不加索引：先用现有 `idx_messages_room_id (room_id, id)`，一间小屋 30 天的量级够用（我的决定）。
3. **小屋通知上限**：`scope=room` 的消息，每人每间小屋每天 **10 条**（文本与短语都算）。
   - 这个数字是**我的建议，用户还没确认**，写成一个常量。
   - “天”按发送者时区（`LocalDayBounds`，与润色配额一致）；从 `messages` 表计数，被审核拦下的没有入库，不计。
   - 位置：查重放之后、前置审核之前，所以重放不受限。并发首发最多多放过一两条，可接受。
   - 超出：429 `RATE_LIMITED`，`Retry-After` 为距下一个零点的秒数，`error.details.reason = "notice_daily"`。已有的每分钟 / 每日限流不带 `reason`，前端靠这个区分文案。
   - 私聊不受此限制。

## 6. 前端设计

### 6.1 结构

```
lib/core/db/                     drift 数据库：每个用户一个文件，登出时删除
lib/features/chat/
  application/
    conversation.dart            会话键：小屋通知(roomId) | 私聊(roomId, peerId)
    chat_message.dart            领域消息、delivery 状态
    message_merge.dart           合并规则（纯函数）
    chat_sync.dart               订阅 coordinator，入库、补消息
    chat_sender.dart             outbox、发送、重试
    unread.dart                  未读（F3b）
    phrases_provider.dart        短语（F3b）
  data/
    chat_repository.dart         REST
    chat_store.dart              drift 读写
  presentation/
    chat_tab.dart                会话列表
    dm_page.dart                 私聊页
    notice_page.dart             小屋通知页
    widgets/                     courier_card、own_bubble、input_bar、phrase_bar
assets/phrases/phrases.json      短语兜底（F3b）
```

- 依赖方向不变：chat 只读 room / auth 的 `application` 层。
- `RealtimeCoordinator` 加两个输出：`message.*` 帧流、“某房间收到快照”流；只转发仍在列表中的房间（沿用现有的 `_rooms` 判断）。`chat_sync` 由 `PetBridgeApp` 保持存活，不看聊天页时也能更新未读。
- 新依赖：`drift`、`drift_flutter`、`drift_dev`（已用 `flutter pub add --dry-run` 确认与 Flutter 3.50 可解析）。**不引入 `connectivity_plus`**（我的决定）：补发时机用“WS 进入 ready”和“回到前台”，与 F2 不监听网络变化的做法一致。TRD 里的 `messages_cache` / `outbox` / `phrases_cache` 沿用。

### 6.2 路由与导航

| 路由 | 页面 |
| :-- | :-- |
| `/home/chat` | 会话列表（替换占位页） |
| `/room/:id/notice` | 小屋通知 |
| `/room/:id/dm/:userId` | 与某成员的私聊 |

- 取代 TRD 的 `/room/:id/chat`。两个详情页全屏，不带底部导航。
- 进入时该房间不在我的房间列表、对方是自己、或自己是未成年人进私聊：返回 `/home/chat`。房间列表加载失败（且没有旧数据）时显示错误与重试，不当作“房间不存在”。
- 停在详情页时被移出 / 解散 / 退出：关掉页面回到 `/home/chat`，提示沿用 F2 的“你已离开该小屋”。


（图里的表情只是示意；实际用 `PetView` 与图标。）

- 与小屋 Tab 共用选中的小屋。会话属于某间小屋：和同一个人同屋两间时，是两个独立会话。
- 成员行：当前在席的其他成员；有消息的按最后一条时间倒序，没消息的按座位号排在后面。宠物离线时用 `sleep` 姿态。
- 预览：自己发的显示“我：原文”；别人发的显示译文，没译好显示原文；小屋通知带发送者昵称。只有一行，超出省略。
- 昵称为空用宠物名（同 F2）。
- 未成年人：只有“小屋通知”一行。
- `solo` 且选中的是自己的小屋：显示“邀请朋友后就能在这里聊天”与“邀请朋友”“输入验证码”按钮。小屋通知里有历史时仍可进入查看。只有自己时不能发通知（没有接收者），输入栏置灰并说明。
- 房间列表加载中 / 失败：与小屋 Tab 相同的加载与重试。

### 6.4 私聊页与小屋通知页

| | 私聊页 | 小屋通知页 |
| :-- | :-- | :-- |
| 样式 | 左右排列：对方是信使卡片，自己是右侧气泡 | 公告板：所有人都是整宽卡片，自己的标“我” |
| 标题 | 对方昵称 | 小屋通知 |
| 顺序 | 旧在上、新在下，打开时停在最新 | 相同 |
| 输入提示 | “对 {昵称} 说…” | “发一条通知给全屋…” |
| 条数限制 | 无（仅通用限流） | 每天 10 条，超出由服务端拒绝 |
| 回复 | — | 没有 |

- 按天插入日期分隔；每条显示时分（本地时区）。
- 翻页：滚到顶拉该会话 `before=<该会话本地最旧 id>` + 筛选条件，每页 30 条，到头为止。
- 新消息到达：停在底部时自动滚动；正在看上面时显示“有新消息”按钮，不抢滚动位置。
- 输入：去首尾空白后 1–500 字（按 Unicode 字符计，与服务端一致）；超出不能发送并显示剩余字数。发送后清空。离开页面时保留未发送的草稿（仅内存）。
- 对方离开小屋：私聊行从列表消失；若正停在私聊页，显示“TA 已离开这间小屋”，停用输入，历史可看。对方重新加入后恢复。

### 6.5 信使卡片

- 头部：发送者宠物（`PetView`）+ 昵称（空用宠物名）+ 时间。实时到达的卡片播放一次约 400ms 的宠物递送动画；历史与补回的不播放。系统开启“减少动态效果”时不播放。
- 正文默认显示：`polish_status = done` → 润色；否则 `translation_status = done` → 译文；否则原文。
- 切换（本地状态，不保存）：
  - 有润色：润色 / 译文 / 原文。
  - 只有译文：译文 / 原文。
  - 源语言 = 目标语言、译文与原文相同，或短语：不显示切换。

| 状态 | 显示 |
| :-- | :-- |
| `translation pending` | 原文 + 译文骨架“翻译中” |
| `translation failed` | 原文 + “暂无法翻译”，**没有重试按钮**；之后收到 `message.translated` 自动换成译文 |
| `translation done` | 译文 |
| `polish pending` | 译文 + 润色加载中 |
| `polish fallback` | 译文 + “未润色”，不再显示按钮 |
| 收到 `message.removed` | 卡片直接消失 |

- “让 AI 润色”（F3b）：只在 `kind = text`、`translation = done`、`polish = none` 时显示；点击后立即显示加载并禁止连点，返回后以服务端视图为准。

### 6.6 合并规则（纯函数，单元测试）

1. 按 `message.id` 插入或更新，与到达顺序无关；所有来源（REST、WS、发送响应）都走这里。
2. `translation_status` 只按 `pending < failed < done` 前进；`polish_status` 只按 `none < pending < done / fallback` 前进。两个状态分别判断，较旧的一侧不覆盖较新的一侧（连同 `base_text` / `polished_text`）。
3. 自己的消息带 `client_msg_id`：用它把 outbox 里的本地气泡换成服务端消息；别的设备发的直接插入。
4. 归属：`scope = room` → 小屋通知；`scope = dm` → 与“不是我的那一方”的私聊。
5. `message.removed`：删本地消息并记住 id（App 生命周期内），迟到的事件不再插入。

### 6.7 同步与补消息

TRD 规则 11 只写“用本地最新消息 id 补”，有三个漏洞：补消息途中先来了实时消息，会让“最新 id”跳过中间那段；并发写入可能让较小的 id 晚出现；断线期间的译文更新和撤回不会作为新消息返回。改为：

- **每间房存一个 `sync_cursor`**（drift）：只有补消息的分页、或已补完之后的实时消息能推进它；补消息进行中的实时消息只入库、不推进。
- **补消息**（混合接口，不加筛选；`limit=100`，`has_more` 就继续）在每次收到该房间快照后进行。起点取以下两者中较早的：
  - `sync_cursor` 的时间往前 10 秒；
  - 最近 24 小时内仍未定的消息（翻译 `pending` / `failed`，或润色 `pending`）中最早的一条再往前 1 毫秒。
  - 起点是按 UUIDv7 时间位拼出的 id（随机位全 0），服务端只要求它是 UUID。
- **对账**：一次补消息完整成功后，本地已有、落在该范围内、接口却没返回的他人消息，删掉（被撤回或被屏蔽）。补消息期间新到的 id 不参与。中途失败不删。
- **首次**（该房间没有 cursor）：取混合最新一页 100 条，cursor 设为最新一条；空列表则记“已同步、无消息”，之后的补消息从头取。
- **打开会话**：拉该会话最新一页 30 条入库，并按这一页覆盖的范围对账。每个会话记录“是否已到最早一条”。`sync_cursor` 之前的部分是连续的，之后可能因补消息失败而有空洞，所以该房间补消息还没完成时，打开会话先触发一次补消息，再允许往前翻。
- 同一房间同时只跑一个补消息；期间又收到快照，跑完再补一次。失败静默，等下一次快照，或打开会话时再试。
- **清理**：打开数据库时删除 30 天前的消息；离开小屋（被移出、解散、退出）时删除该房间的消息、outbox、游标与未读。

### 6.8 发送与 outbox

- 点发送：生成 `client_msg_id`（UUID）→ 写 outbox → 气泡“发送中” → `POST`。成功后删 outbox、写消息。
- 每个会话同时只发一条，按先后顺序；前一条失败不阻塞后一条。
- App 启动时把上次停在“发送中”的改回“待发送”。
- F3a：任何可重试的失败都标“发送失败，点按重试”。F3b 起网络类失败自动补发。

| 结果 | 处理 |
| :-- | :-- |
| 202 | 完成。开了润色但 `polish_requested = false`：轻提示“今天的润色次数用完了” |
| 网络错误、超时、5xx、`NOT_READY` | F3b：保持“待发送”，WS ready 或回到前台时补发；累计 3 次仍失败 → 失败，可手动重试 |
| `RATE_LIMITED`（无 reason） | 失败，可重试；提示“发得太快了，稍后再试” |
| `RATE_LIMITED`（`notice_daily`） | 失败，可重试（第二天有效）；提示“今天在这间小屋的通知已经发满了，明天再来” |
| `CONTENT_BLOCKED` | “消息未能送达”，不可重试；原因不说明 |
| `AGE_RESTRICTED` | 失败，不可重试；“未成年人与成年人之间不能私聊”改用独立文案 `chat_dm_restricted`，不沿用入房那条 |
| `VALIDATION_FAILED`（含 `to_user_id`） | 失败，不可重试；“TA 已离开这间小屋” |
| `ROOM_NOT_FOUND` | 按已离开小屋处理 |
| 401 刷新失败 | 会话结束；outbox 留着，同一用户再登录后继续 |

- 手动重试与自动补发**沿用原 `client_msg_id`**，服务端幂等。失败与被拦的气泡可以删除。
- 停留超过 24 小时的待发送消息标记失败，不自动发出；用户仍可手动重试。
- 登出：删除该用户的数据库文件（含 outbox）。`TokenRefresher` 判定会话过期不算登出，不删；换一个用户登录时用另一个文件，互不可见。
- Android 自动备份排除该数据库（聊天内容不上云备份，我的决定）。

### 6.9 未读（F3b）

- 每个会话存 `last_read_id`；未读 = 他人发来且 id 更大的消息数，最多显示 99+。
- 首次同步某房间时，以 `sync_cursor` 为基线：重装后历史消息不算未读；之后新到的都算。
- 会话页在前台可见时，读到的最新一条即为已读；切后台不算。
- 显示位置：会话行、底部“聊天”图标（两间小屋合计）、小屋切换上的圆点（另一间有未读）。
- 只存本机，不同步到其他设备（已读接口随 B7）。

### 6.10 短语与润色（F3b）

- 短语条：输入框上方横向 8 个，显示我的母语文字，点一下立即发送（不经 AI、不审核）。通知页同样可用，计入每天 10 条。
- 数据：先用随包 `assets/phrases/phrases.json`（由后端 `phrases.go` 生成的同一份内容），再 `GET /config/phrases?v=`；200 更新本地，304 与任何失败都用已有的。五语文字按用户 `native_lang` 取，缺则英文。
- 润色开关：默认关，只影响文本；离开页面恢复为关（避免不知不觉用完次数）。
- “让 AI 润色”失败：`QUOTA_EXCEEDED` 按 reason 四条文案；`POLISH_NOT_READY` / `DELIVERY_NOT_FOUND` 用通用文案并重新拉该会话最新一页；其余按通用错误。失败后按钮恢复。

## 7. 错误码与文案

新增五语文案：`CONTENT_BLOCKED`（消息用）、`QUOTA_EXCEEDED` 四条、`RATE_LIMITED` 的 `notice_daily`、`chat_dm_restricted`、`POLISH_NOT_READY` / `DELIVERY_NOT_FOUND`（落通用）以及各页面文案。原有 `AGE_RESTRICTED`（不能同屋）保留给入房。

`AppFailure` 现有的 `details` 与 `Retry-After` 已够用，不改结构。`IdempotencyInterceptor` / `RetryInterceptor`（TRD 8.1 写明“随发消息阶段加入”）**不加**（我的决定）：幂等以请求体 `client_msg_id` 为准，重试由 outbox 统一负责，两层重试会让失败计数失真。TRD 相应改写。

## 12. 我的决定（可推翻）

- 小屋通知每天 10 条，文本与短语都算。
- 会话属于小屋，不跨小屋合并。
- 通知页按旧到新排列，与私聊一致。
